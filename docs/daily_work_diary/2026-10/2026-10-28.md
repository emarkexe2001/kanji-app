## FEAT6 – Back button (PR #46)
Decided with a mockup (Option B, Back style "outline"):
- **Layout:** the card controls are two rows: **"← Back" | "Next →"**, then **Deck Shuffle** across the full width. All three buttons are 48px tall with rounded-xl corners. Next and Deck Shuffle keep their colours.
- **Look:** Back is an outline button: white, a 1px slate-400 border and slate-900 semibold text, with a light slate hover. The arrow is decorative, so screen readers hear "Back". It has a visible focus ring, and in high-contrast mode its border uses the system ButtonText colour.
- **Where Back goes:**
  - It goes to the last card actually seen, like a browser back button. That includes cards reached with Deck Shuffle and Add Back Cards. Each press goes one card further back.
  - With nothing left to go back to (at the start, or once the history runs out), it goes to the card before in deck order, wrapping from Card 1 to the last card.
  - Next after Back moves on from the card on screen. There is no "forward".
- **The history:**
  - It holds card ids, not positions, and keeps at most the last 50 cards.
  - It is not kept after a reload, and nothing new is saved.
  - Only changing the studied deck clears it. Deck Shuffle, Shuffle In Cards and card limit changes keep it.
  - Cards no longer in the deck are skipped, so Back never shows a missing card.
- **NEW ribbon:** going Back counts as moving on from the card on screen, exactly like Next.
- **Keyboard:** ← works as Back, except while typing in a field. The hint now reads "Keyboard: ← back · → next · S deck shuffle".
- **Animation:** the card slides in from the left, the opposite way to Next. This is skipped with reduced motion on, and ADJ3 may refine it.
- **Tests:** 25 new UI tests (`back-button.test.tsx`) and 7 new unit tests (`card-history.test.ts`). Deck Shuffle is made predictable in the tests. All 24 break-and-restore checks went red as they should. Totals: UI 237, web unit 35, core 10, scripts 23.
- **Browser check:** the agent checked the layout in Chrome at 360px, 640px and 1024px: two rows, every button 48px, no sideways scrolling. Clicking through Next, Deck Shuffle and Back gave the expected cards. High-contrast mode, the keyboard focus ring and the slide were left for the user to check. Their result isn't recorded on the PR.

## Decisions made today
- FEAT6 uses Option B (two rows) with an outline Back button.
- Back follows the cards actually seen. With nothing left, it carries on in deck order and wraps.
- Only a change of studied deck clears the history. It holds at most 50 cards and is not kept after a reload.
- Back clears the NEW ribbon the same way Next does.
- Back's padding is 1px less than the other buttons' so that, with its border, it is 48px tall like them. The agent chose this after the browser check.

## Process lessons
- **The browser check found a bug the tests couldn't.** Back's 1px border made it 50px tall, which stretched Next in the same row to 50px. It was fixed before the PR opened.
- **Break-and-restore found a test that couldn't fail.** The first version of the "changing the studied deck clears the history" test pressed Back on the new deck first. Skipping the old deck's cards emptied the history by itself, so breaking the clear didn't turn the test red. The test now switches straight back to the first deck.
- **Check what each commit stages.** The ticket's move into `completed_tickets/` was already staged, so it went into a test-fix commit. It was explained in the next commit message instead of rewriting history.
- **The Chrome extension was connected this time,** so the agent could check the layout itself. Its window couldn't be resized, so the app was measured in iframes 360, 640 and 1024px wide. High-contrast mode still needs a person.
- **PR #46 was merged with no peer review or browser-check result recorded on it.** Next time, post them as PR comments before merging, so the record shows they were done.

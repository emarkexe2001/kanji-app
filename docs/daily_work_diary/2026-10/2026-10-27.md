## FEAT3 – Shuffle in from multiple decks (PR #43)
Decided with a mockup (Option B):
- **The switch:** the "Shuffle in from" dropdown is replaced by a three-way switch, **One deck | Random | Multiple decks**. It is a real radio group (fieldset, legend and native radio buttons drawn as segments). The chosen segment is emerald-700 with white text (passes 4.5:1). Arrow keys work, and it uses the system Highlight colours in high-contrast mode.
- **One deck:** a full-width deck dropdown underneath, with a hidden label for screen readers ("Deck to shuffle in from"). Works as in FEAT1.
- **Random:** nothing extra shows. Works as in FEAT1.
- **Multiple decks:** a "Decks to shuffle in from" box with a checkbox for each other deck, 2 per row. The studied deck is never offered. Nothing is ticked at first.
- **Picking:** the new cards of the ticked decks are pooled, each card once, and picked at random. A card in two ticked decks (e.g. JLPT N4 and Common words) counts as coming from the first one in deck order.
- **Rules:** two or more decks must be ticked. With fewer than two other decks, Multiple decks is disabled with the hint "Needs at least two other decks."
- **Messages:** red alerts for none ticked, one ticked and not enough new cards ("1 new card" for one; a separate message when none are left). An amber notice names any ticked deck that is gone after a reload or is now the studied deck. It only shows when Multiple decks was the chosen mode; otherwise the tick is dropped silently. All messages clear when the ticks, mode, count, studied deck or card limit change.
- **Saved:** the mode, the One deck choice and the ticks are remembered after a reload, and the ticks are kept while another mode is used. Choices saved before FEAT3 still load.
- **Tests:** 37 new UI tests (`shuffle-in-multiple.test.tsx`) and 5 new unit tests. Every rule was checked with break-and-restore. Totals: UI 212, web unit 28, core 10, scripts 23.
- **Review:** fixes went in before merging (missing break-and-restore checks, a wrong test comment, a deck saved twice now counts as one tick). The PR was kept as draft with a "Do not merge yet" comment until they landed.
- **Browser check:** done by the user at about 360px, 640px and 1024px, including high-contrast mode.

## FEAT6 – Back button (ticket only, PR #44)
- Back goes to the **last card actually seen**, like a browser back button, including cards reached with Deck Shuffle.
- **At the start**, with nothing earlier seen, Back wraps to the last card in the deck, the same way Next wraps.
- Still open, for the mockup stage: placement and label, history after a reload, what clears the history, history limit, slide direction and the NEW ribbon.

## Decisions made today
- FEAT3 uses Option B (three-way switch) and combined random picking.
- The chosen segment is emerald-700, not emerald-600, so white text passes contrast. The Shuffle In Cards button stays emerald-600.
- No extra notice when a saved Multiple decks choice falls back to One deck. The greyed hint is enough.
- A deck that was unticked because it was gone is not ticked again if it comes back.
- FEAT6: Back follows the cards actually seen and wraps at the start.

## Process lessons
- **Standards 5.4 worked.** PR #43 went to draft with a "Do not merge yet" comment while review fixes were pending, so it was not merged early (unlike PR #36 last week).
- **Break-and-restore finds flaky tests.** A break run showed the "switch back to Random" test could fail by chance (about 2%). Its decks were resized so the test is now deterministic.
- **The feature agent couldn't do the browser check** because the Chrome extension wasn't connected. The user did it instead. Check the extension is connected before starting a ticket with UI changes.
- **Choices made without a mockup should be recorded in the ticket.** Three such choices in FEAT3 (full-width dropdown, the no-cards wording, notice only under Multiple decks) were agreed in review and added to the ticket afterwards.
